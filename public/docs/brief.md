# แผนพัฒนา XEDO Satellite Dashboard

ฉบับส่งต่อเพื่อพัฒนา 1.1 — 4 ตุลาคม 2026

**เป้าหมาย:** พัฒนาต้นแบบ dashboard ที่ใช้ภาพดาวเทียมจริง ช่วยระบุพื้นที่ที่ควรตรวจสอบ เก็บหลักฐานตรวจยืนยัน และส่งต่อขอบเขตพื้นที่ให้ทีมสำรวจด้วยโดรน โดยตรวจย้อนกลับได้ว่าข้อมูลแต่ละชิ้นมาจากไหนและบันทึกเมื่อไร

เอกสารนี้เป็นแผนพัฒนา ไม่ใช่รายงานว่าฟังก์ชันเหล่านี้ทำสำเร็จแล้ว พื้นที่นำร่อง วันส่งงาน จำนวนผู้พัฒนา งบประมาณ บัญชีข้อมูลดาวเทียม และชุดข้อมูลฝึก AI ยังรอข้อมูลจากผู้ใช้ แผนสามารถปรับได้โดยไม่ต้องเปลี่ยนเป้าหมายหลัก

## 0. บริบทและคำสั่งสำหรับนำไปสร้างในแชตใหม่

### บริบทโครงการที่ต้องรู้

ผู้ใช้เตรียมโครงการนวัตกรรมสำหรับ iENA ที่เยอรมนี งานเดิม ODEX ศึกษาโดรนและระบบปล่อยไมโครแคปซูลแอลจิเนต/ขี้ผึ้งบรรจุจุลินทรีย์ Rhodococcus erythropolis และ Bacillus เพื่อช่วยบำบัดน้ำมันในพื้นที่ป่าชายเลน แผน XEDO ขยายด้วยข้อมูลดาวเทียม GeoAI และ dashboard สนับสนุนการสำรวจและการตอบสนอง

งานที่จะสร้างจากเอกสารนี้เน้น **ส่วน dashboard ที่เชื่อมข้อมูลดาวเทียม** โดยรองรับการส่งต่อพิกัดและรับหลักฐานจากโดรนไว้ด้วย รายละเอียดเรื่อง dose กลไกปล่อย และผลชีวบำบัดเป็นโมดูลที่จะเชื่อมภายหลัง

ผู้ใช้ต้องการสื่อสารภาษาไทยที่เข้าใจง่าย และแยกข้อมูลสามประเภทให้ชัด: สิ่งที่อยู่ในไฟล์ผู้ใช้ สิ่งที่ค้นจากเว็บ และข้อเสนอการออกแบบของผู้ช่วย หากอ้างข้อเท็จจริงจากเว็บให้มีลิงก์ต้นทาง

### ข้อความที่คัดลอกไปใช้เปิดงานได้

> กรุณาพัฒนา XEDO Satellite Dashboard ตามแผนในไฟล์นี้ เริ่มจากระยะ 0–2 และงาน P0 ให้ทำงานครบตั้งแต่เลือกพื้นที่ ค้นหาและแสดงภาพดาวเทียมจริงพร้อมแหล่งและวันเวลา วงขอบเขต บันทึกเหตุการณ์ แนบหลักฐาน ไปจนถึงส่งออก GeoJSON/CSV ข้อมูลต้องเปิดกลับมาได้หลังเริ่มระบบใหม่
>
> ตรวจ workspace และคำแนะนำโครงการก่อนแก้ไฟล์ หากมีต้นแบบ XEDO อยู่แล้วให้ประเมินและใช้ส่วนที่เหมาะสมต่อ รักษางานเดิมและการเปลี่ยนแปลงของผู้ใช้ หากเป็น workspace ใหม่ให้สร้างโครงการจากข้อกำหนดในเอกสารนี้ ใช้แผนเป็นฐานและอธิบายเมื่อมีเหตุให้ปรับเทคโนโลยีหรือขอบเขต
>
> เริ่มทดลองค้น catalogue และขอภาพขนาดเล็กเพื่อพิสูจน์การเข้าถึงข้อมูล แล้วพัฒนาฐานข้อมูล API แผนที่ และ workflow ตรวจสอบให้ครบ หากยังขาดบัญชีหรือสิทธิบริการ ให้ทำงานส่วนที่ไม่ขึ้นกับสิทธิต่อ และระบุว่าการขอภาพจริงส่วนใดรอตั้งค่า พร้อมวิธีตั้งค่าที่ไม่เปิดเผย secret ในแชตหรือหน้าเว็บ
>
> ระยองใช้เป็นพื้นที่ตัวอย่างสำหรับการออกแบบได้จนกว่าจะเลือกพื้นที่นำร่อง และต้องเปลี่ยนพื้นที่ได้ อย่าแสดงข้อมูลจำลองหรือผล AI ตัวอย่างเป็นการตรวจพบจริง ผลจากผู้ใช้กับผลจากระบบต้องระบุแหล่งต่างกัน ไม่มีข้อมูลหรือประมวลผลไม่สำเร็จต้องแสดงสถานะตามจริง
>
> เพิ่ม baseline/AI หลังมีภาพ ชุดข้อมูล และเกณฑ์ประเมินรองรับ โดยแยกจากการส่งมอบ MVP ไม่ใช้ผลแม่นยำจากภาพโดรนเป็นผลของโมเดลดาวเทียม ตรวจรับตามเกณฑ์ในแผน เปิดตัวอย่างใช้งานให้ดู และรายงานสิ่งที่ทำสำเร็จ ผลทดสอบ และส่วนที่ยังรอข้อมูลเป็นภาษาไทย

## 2. ขอบเขตที่เสนอและสมมติฐานตั้งต้น

**รุ่นแรก: ภาพจริง + ผู้ใช้ตรวจ + บันทึกเหตุการณ์ + ส่งออกพิกัดสำรวจ**

- เริ่มหนึ่งพื้นที่นำร่อง ซึ่งผู้ใช้สามารถเปลี่ยนได้ ตัวอย่างระยองอ้างอิงจากต้นแบบหน้าจอปัจจุบันเท่านั้น ยังไม่ถือว่าผู้ใช้เลือกแล้ว
- ใช้งานหลักบนคอมพิวเตอร์; มือถือใช้เปิดดูรายการ ภาพ และแนบหลักฐานได้ การวาดขอบเขตละเอียดให้ใช้หน้าจอใหญ่
- เริ่มระบบส่วนตัวสำหรับทีมโครงการ สามารถรันในเครื่องหรือบนเซิร์ฟเวอร์ของทีมตามที่เลือกภายหลัง
- ภาพย้อนหลังที่มีหลักฐานยืนยันเป็นข้อมูลทดสอบสำคัญ ไม่จำเป็นต้องรอเกิดเหตุใหม่เพื่อทดสอบ dashboard
- ข้อมูลจริง ข้อมูลที่ผู้ใช้ตีความ ผล AI และข้อมูลสถานการณ์จำลองมีประเภทแยกกัน ทุกประเภทต้องส่งต่อไปพร้อมไฟล์ export
- ภาพดาวเทียมใช้เฝ้าระวังผิวน้ำและบริบทชายฝั่ง ส่วนรายละเอียดใต้เรือนยอดป่าชายเลนและผลบำบัดต้องอาศัยหลักฐานภาคสนามตามความเหมาะสม

**งานในระยะถัดไป:** AI คัดกรองภาพ การจัดลำดับพื้นที่สำรวจ การรับข้อมูลโดรน และการติดตามเหตุการณ์หลายช่วงเวลา

**แยกเป็นงานต่อยอด:** การทำนายการเคลื่อนที่ของน้ำมัน ระบบสั่งบินอัตโนมัติ ฝูงโดรน การคำนวณปริมาณแคปซูล และการประเมินประสิทธิภาพชีวบำบัด งานเหล่านี้มีข้อมูลและการทดสอบเฉพาะที่ต้องทำเพิ่ม

## 3. คำถามที่ dashboard ต้องตอบ

| คำถามผู้ใช้ | หลักฐานที่ต้องมี | วิธีแสดง | สิ่งที่ทำต่อได้ |
|---|---|---|---|
| พื้นที่นี้มีภาพอะไรให้ดู? | รหัสภาพ ขอบเขต วันเวลาถ่าย แหล่งข้อมูล | แผนที่และรายการภาพ | เลือกภาพที่เหมาะสม |
| ภาพนี้ใช้ตรวจได้แค่ไหน? | พื้นที่มีข้อมูล เมฆ/เงาสำหรับภาพสี และข้อจำกัดภาพเรดาร์ | สถานะคุณภาพและพื้นที่ที่ประเมินไม่ได้ | เปลี่ยนภาพหรือส่งสำรวจ |
| ตรงไหนน่าสงสัย? | ขอบเขตที่ผู้ใช้วง หรือผลวิเคราะห์ที่ระบุรุ่นและพารามิเตอร์ | polygon บนภาพต้นทาง | เปิดตรวจ แก้ไข หรือบันทึกเหตุ |
| จุดนี้ยืนยันหรือยัง? | บันทึกผู้ตรวจ ภาพ/ผลภาคสนาม วันเวลาตรวจ | รายละเอียดเหตุการณ์และประวัติ | ยืนยัน ปฏิเสธ หรือคงสถานะไม่แน่ชัด |
| ควรส่งทีมไปตรวจที่ไหน? | เหตุที่รอตรวจ อายุข้อมูล ความใกล้พื้นที่เปราะบางเมื่อมีแหล่งข้อมูล | รายการงานสำรวจ | ส่งออกขอบเขตและหมายเหตุ |
| เหตุการณ์เปลี่ยนไปอย่างไร? | ภาพหลายเวลาและผลตรวจที่เทียบกันได้ | ภาพคู่และ timeline | นัดตรวจซ้ำหรือปิดเหตุด้วยหลักฐาน |

กราฟและการ์ดตัวเลขจะเพิ่มเฉพาะเมื่อมีข้อมูลรองรับ เช่น จำนวนเหตุที่รอตรวจ จำนวนเหตุยืนยัน และพื้นที่ที่ถูกวงในภาพที่เลือก ไม่เติมตัวเลขเพื่อให้หน้าจอดูเต็ม

~~~

**แยก observation กับ incident:** observation คือสิ่งที่เห็นในภาพหนึ่งครั้ง; incident คือเหตุการณ์ที่รวบรวม observation และหลักฐานหลายครั้ง เหตุเดียวจึงมีหลายภาพได้โดยไม่เพิ่มจำนวนเหตุซ้ำ

สถานะของ observation: ร่าง → เสนอให้ตรวจ → ตรวจแล้ว/ไม่แน่ชัด → เก็บประวัติการแก้ไข

สถานะของ incident: สงสัย → รอตรวจ → ยืนยันพบ/ไม่ยืนยัน/ยังไม่แน่ชัด → ติดตาม → ปิดเหตุพร้อมเหตุผล สามารถเปิดกลับได้เมื่อมีหลักฐานใหม่

ผลไม่พบในภายหลังไม่ลบสิ่งที่เห็นในภาพก่อนหน้า เพราะช่วงเวลาต่างกัน ต้องบันทึกว่าไม่พบเมื่อไรและด้วยวิธีใด การกดตรวจภาพเสร็จไม่เท่ากับยืนยันน้ำมันโดยอัตโนมัติ

## 5. โครงหน้าจอ

### 5.1 หน้าสำรวจดาวเทียม — หน้าหลัก

- แถบเลือกพื้นที่ ช่วงวันที่ ชนิดดาวเทียม และตัวกรองที่เหมาะกับแหล่งข้อมูล
- รายการภาพที่มีวันเวลาถ่าย แหล่งข้อมูล และสถานะพร้อมดู/กำลังเตรียม/มีข้อจำกัด
- แผนที่กลางหน้าจอ รองรับเลื่อน ซูม มาตราส่วน พิกัด และเปิดปิดชั้นข้อมูล
- ชั้นหลัก: ภาพที่เลือก พื้นที่ไม่มีข้อมูล เมฆ/เงาที่ตรวจได้ ขอบเขตผู้ใช้วง ผลคัดกรอง และหลักฐานโดรนที่มีพิกัด
- แผงรายละเอียดภาพและ observation ด้านข้าง กดบน polygon แล้วเปิดรายการเดียวกัน
- เครื่องมือวาด แก้ไข และลบ polygon ก่อนบันทึก โดยการแก้ไขที่บันทึกแล้วเก็บเป็น revision
- ภาพเปรียบเทียบสองเวลา พร้อมป้ายวันที่ทั้งสองฝั่ง ระบุเมื่อชนิดข้อมูลหรือเงื่อนไขต่างกัน
- แผนที่พื้นหลังอ้างอิงแยกจากภาพ Sentinel ที่เลือก ป้ายแหล่งและเวลาไม่ปะปนกัน
- สถานะโหลด ไม่มีภาพ ประเมินไม่ได้ API ขัดข้อง และผลคัดกรองไม่พบพื้นที่ มีข้อความต่างกัน

### 5.2 หน้ารายการเหตุการณ์

- รายการเรียงตามงานที่ต้องตรวจและวันที่ โดยมีตัวกรองพื้นที่ สถานะ และช่วงเวลา
- แต่ละรายการมีรหัสเหตุ ตำแหน่ง ภาพต้นทาง อายุข้อมูล สถานะ และเหตุผลที่เสนอให้สำรวจ
- การคลิกพาไปตำแหน่งบนแผนที่และรายละเอียดเดียวกัน
- สรุปจำนวนเหตุใช้รหัส incident ที่ไม่ซ้ำ; จำนวน observation แสดงเป็นอีกตัวเลขเมื่อจำเป็น
- รวมเหตุหรือแยกเหตุโดยผู้ตรวจ พร้อมประวัติ ไม่รวมอัตโนมัติจาก polygon ทับกันเพียงอย่างเดียว

### 5.3 รายละเอียดเหตุการณ์

- ภาพต้นทางและขอบเขตทุกครั้งที่เกี่ยวข้อง
- timeline ของภาพ ผลคัดกรอง การตรวจภาพ ภาคสนาม และการเปลี่ยนสถานะ
- แนบภาพโดรน ผลตรวจ เอกสาร และหมายเหตุ พร้อมวันเวลาและตำแหน่ง
- ระบุวิธียืนยัน ระดับหลักฐาน และความสัมพันธ์ด้านเวลากับภาพดาวเทียม
- แสดงขอบเขตต้นฉบับของระบบและขอบเขตที่ผู้ใช้แก้ แยกกันได้
- ปุ่มส่งออกขอบเขต พิกัด รายงานเหตุการณ์ และสร้างคำขอสำรวจ

### 5.4 หน้างานสำรวจ

- รายการพื้นที่ที่จะตรวจ ขอบเขตและจุดอ้างอิง เวลาในภาพต้นทาง และหมายเหตุ
- สถานะคำขอ: ร่าง → พร้อมสำรวจ → กำลังสำรวจ → มีผลตรวจ → ปิดงาน
- นำเข้า/แนบผลจากทีมโดรนและเชื่อมกลับ incident เดิม
- รุ่นแรกส่งออก GeoJSON และ CSV; การสร้างไฟล์ mission สำหรับ flight controller ต้องระบุอุปกรณ์และทดสอบเพิ่มก่อน
- คำขอสำรวจเป็นการส่งต่อข้อมูลพื้นที่ ไม่ใช่คำสั่งบินอัตโนมัติ

### 5.5 หน้ารายงานและการตั้งค่า

- รายงานเหตุการณ์: แหล่งข้อมูล ภาพ ขอบเขต timeline หลักฐาน และข้อจำกัด
- สรุปตามช่วงเวลาเมื่อมีข้อมูลจริงเพียงพอ โดยระบุส่วนที่ตรวจแล้วและส่วนที่ยังไม่ทราบ
- ตั้งค่า AOI บัญชีการเชื่อมต่อ ขอบเขตงานสูงสุด ค่าเริ่มต้น และการเก็บไฟล์
- รายการงานประมวลผลแสดงสถานะ ความล้มเหลว และลองใหม่ได้ รายละเอียดทางเทคนิคอยู่ในส่วนดูเพิ่มเติม
- ส่วนจัดการชุดข้อมูล/เทรนโมเดลสำหรับผู้พัฒนาแยกจาก workflow ผู้สำรวจ ปุ่มในหน้าจอจะสะท้อนงานจริงที่ backend ทำเท่านั้น

## 6. การเลือกและเชื่อมข้อมูลดาวเทียม

**ข้อเท็จจริงจากเว็บ:** CDSE มี STAC สำหรับค้นหาข้อมูลเชิงพื้นที่และเวลา และ Sentinel Hub API สำหรับขอภาพตามพื้นที่ที่สนใจ รายละเอียดอยู่ใน [STAC](https://documentation.dataspace.copernicus.eu/APIs/STAC.html) และ [Sentinel Hub](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub.html)

| ข้อมูล | บทบาทในแผน | เริ่มใช้เมื่อไร |
|---|---|---|
| Sentinel-2 ภาพสี | ให้ผู้ใช้เข้าใจพื้นที่ ดูบริบท และทดลอง workflow กับภาพจริง | การเชื่อมภาพจริงครั้งแรก |
| Sentinel-1 GRD เรดาร์ | ดูสัญญาณบนผิวน้ำและพัฒนาการคัดกรองพื้นที่สงสัย | เชื่อมหลังยืนยันการดึงภาพและแผนที่ทำงานครบ แล้วใช้เป็นแกนการทดลองคัดกรอง |
| ภาพโดรน/หลักฐานภาคสนาม | ตรวจรายละเอียดและประกอบการยืนยัน | ระบบแนบหลักฐานใน MVP |
| ชายฝั่ง/ป่าชายเลน/พื้นที่เปราะบาง | บริบทเพื่อเลือกพื้นที่สำรวจ | เมื่อมีแหล่งที่มา สิทธิใช้งาน และวันที่ของข้อมูล |
| ลม กระแสน้ำ และ AIS | ประกอบการวิเคราะห์และการทดลองต่อยอด | ระยะถัดไปเมื่อมีบริการข้อมูลและความต้องการชัดเจน |

**ข้อเท็จจริงจากเว็บ:** ESA ระบุว่า SAR เป็นเทคโนโลยีหลักสำหรับตรวจคราบน้ำมันนอกชายฝั่ง แต่สัญญาณคล้ายคราบน้ำมันอาจเกิดจากสาหร่ายและลักษณะผิวน้ำอื่น ภาพสีมีข้อจำกัดจากเมฆ แสง และ sun-glint จึงใช้ผลเป็นพื้นที่สงสัยก่อนการยืนยัน [ESA Oil Slicks](https://knowledge-hub-gda.esa.int/eo_capability/oil-slicks/)

**ข้อเท็จจริงจากเว็บ:** Sentinel-2 มีแบนด์ที่ความละเอียด 10, 20 และ 60 เมตร และเก็บภาพตามรอบภารกิจ ดังนั้นการซูมหน้าจอไม่ทำให้ข้อมูลมีรายละเอียดเพิ่มขึ้น และคำว่าอัปเดตต้องผูกกับวันถ่ายจริง [SentiWiki](https://sentiwiki.copernicus.eu/web/s2-mission)

ขั้นเชื่อมข้อมูลที่เสนอ:

1. รับ AOI และช่วงเวลา ตรวจ polygon/ขนาดคำขอ แล้วค้นหา catalogue
2. อ่านทุกหน้าของผลค้นหา หรือแสดงขอบเขตว่าดึงมาเพียงบางส่วน จัดรายการตามวันเวลาถ่าย
3. บันทึก product ID, collection, footprint และ metadata สำคัญก่อนขอภาพ
4. ขอภาพที่เลือกจากบริการประมวลผลผ่าน backend โดยระบุพื้นที่ แบนด์ พิกัด และขนาดภาพ
5. ตรวจว่าภาพตอบกลับตรงพื้นที่และวันเวลา เก็บผลและ metadata ให้เปิดซ้ำได้
6. แสดงภาพจริงบนแผนที่และบันทึก transform ที่ใช้แปลงพิกัดภาพกับพิกัดภูมิศาสตร์
7. ขอซ้ำด้วย scene และพารามิเตอร์เดิมให้ใช้ cache แทนการใช้โควตาซ้ำ
8. เปลี่ยนข้อมูลหรือพารามิเตอร์ให้สร้างรายการประมวลผลใหม่ ตรวจย้อนกลับได้

สำหรับการตีความเหตุการณ์ ใช้ภาพที่ระบุ acquisition ชัดเจน ถ้าต้องประกอบหลายภาพ ให้เก็บรหัสและเวลาของภาพที่ร่วมประกอบทั้งหมด การสร้างภาพรวมหลายวันต้องมีป้ายว่ามีหลายเวลา

**เงื่อนไขเข้าถึง:** การค้นหา catalogue และการดาวน์โหลด/ประมวลผลภาพเป็นคนละขั้น ต้องทดลองสิทธิจริงแยกกัน ผู้ใช้ต้องมีบัญชีและตั้งค่า OAuth สำหรับวิธีที่เลือก โดยเก็บ secret ฝั่ง backend ผ่านการตั้งค่าที่ปลอดภัย [การยืนยันตัวตน](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub/Overview/Authentication.html)

บริการมีโควตาและข้อจำกัดด้านการประมวลผล ระบบต้องจำกัดขนาดคำขอ จัดคิว เก็บ cache และแสดงเหตุผลเมื่อโควตาไม่พอ งบประมาณจึงต้องพิจารณาทั้งการเข้าถึงข้อมูล เครื่องประมวลผล และพื้นที่เก็บ [โควตาทางการ](https://documentation.dataspace.copernicus.eu/Quotas.html)

## 7. การเตรียมข้อมูลและคุณภาพ

### 7.1 Sentinel-2

- ใช้ผลิตภัณฑ์พร้อม metadata เช่น L2A สำหรับการแสดงภาพและการทดลองตั้งต้น โดยทดสอบว่าเหมาะกับบริบทน้ำชายฝั่งที่เลือก
- เก็บแบนด์ต้นทางและค่า nodata เมื่อจะวิเคราะห์ ไม่ใช้ภาพหน้าจอหรือภาพ RGB ที่ปรับสีแล้วแทนข้อมูลเชิงตัวเลข
- บันทึก cloud cover ของทั้ง scene แยกจาก cloud/valid coverage ใน AOI; ตัวเลขทั้งสองไม่เท่ากัน
- ประเมินเมฆ เงา และพื้นที่ไม่มีข้อมูลภายใน AOI เมื่อมี mask รองรับ พร้อมระบุวิธีและรุ่น
- เมื่อใช้แบนด์ต่างความละเอียดร่วมกัน บันทึกการ resample และความละเอียดของ grid วิเคราะห์; การ resample ไม่เพิ่มรายละเอียดต้นทาง
- ใช้ค่าปรับสีเพื่อการดูภาพเป็นอีกชุดพารามิเตอร์หนึ่ง ไม่ปะปนกับพารามิเตอร์โมเดล

### 7.2 Sentinel-1

- บันทึก product mode, polarization, orbit direction/relative orbit, มุมตกกระทบเมื่อมี และชนิด backscatter
- ระบุขั้น calibration/noise removal, การแก้เรขาคณิต และการกรอง speckle ที่ใช้ พร้อมเก็บพารามิเตอร์
- การแสดงภาพ dB กับการวิเคราะห์ linear power ต้องระบุหน่วยและวิธีแปลง ไม่ใช้ threshold ชุดเดียวปะปนหน่วย
- เมื่อเทียบหลายเวลา ตรวจความเข้ากันของ orbit, polarization, grid และ geometry ก่อน
- ใช้ mask แยกน้ำกับแผ่นดินเมื่อมีข้อมูลที่เหมาะสม และเก็บข้อผิดพลาดที่ชายฝั่ง/น้ำขึ้นลงไว้ทดสอบ
- ระบุขอบเขตที่โมเดลใช้ประเมินได้ หากเงื่อนไขของภาพอยู่นอกชุดทดสอบให้แสดงข้อจำกัด

ความสามารถประมวลผลข้างต้นตรวจจาก [เอกสาร Sentinel-1 GRD](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub/Data/S1GRD.html) ส่วนการเลือกค่าที่เหมาะกับโครงการเป็นงานทดลองในแผน ไม่ใช้ค่าเริ่มต้นของบริการเป็นผลพิสูจน์การตรวจน้ำมัน

### 7.3 เวลาและพิกัด

เก็บเวลาอย่างน้อย 5 ประเภท: เวลาถ่ายภาพ เวลารับข้อมูล เวลาวิเคราะห์ เวลาตรวจโดยผู้ใช้ และเวลาตรวจภาคสนาม เก็บใน UTC และแสดงเขตเวลาชัดเจน เช่น Asia/Bangkok

เก็บ polygon ใน WGS84/GeoJSON และคำนวณพื้นที่ด้วยวิธี geodesic หรือระบบพิกัดที่เหมาะกับพื้นที่ ไม่คำนวณพื้นที่จากพิกเซลหน้าจอที่ซูมได้ ใช้ตารางเมตรเป็นค่าหลักแล้วแปลงเป็นไร่/เฮกตาร์/ตารางกิโลเมตรตามหน้าจอ การคำนวณ geography ของ PostGIS รองรับหน่วยตารางเมตร [ST_Area](https://postgis.net/docs/manual-3.7/en/ST_Area.html)

## 8. แผนระบบคัดกรองและ AI

### ระดับ A: ผู้ใช้วงพื้นที่

ต้องทำงานครบได้ก่อน AI: เปิดภาพจริง วาดขอบเขต ใส่เหตุผล บันทึก และส่งออก ระบบรู้แหล่งที่มาว่าเป็นขอบเขตจากผู้ใช้ จึงไม่เติมค่า confidence

### ระดับ B: baseline คัดกรองภาพเรดาร์

ทดลองวิธีตั้งต้น เช่น เปรียบเทียบ backscatter กับบริเวณน้ำใกล้เคียงตามเงื่อนไขที่กำหนด แล้วกรองขนาด/รูปร่างและแปลงเป็น polygon วิธีนี้เป็นการหา anomaly ไม่ใช่การยืนยันน้ำมัน

เก็บ threshold, grid, mask, parameter version และภาพต้นทางทุกครั้ง ผู้ใช้ยอมรับ แก้ไข หรือปฏิเสธแต่ละข้อเสนอได้ ประเมิน baseline ก่อนเลือกเพิ่มความซับซ้อน

### ระดับ C: โมเดล segmentation

- จัดทำชุดข้อมูลดาวเทียมที่มีหลักฐานประกอบ ได้แก่ เหตุที่ยืนยันว่ามีน้ำมัน กรณีคล้ายแต่ไม่ใช่น้ำมัน และกรณียังไม่แน่ชัด
- ความสอดคล้องด้านวันเวลา/ตำแหน่งของหลักฐานต้องบันทึก ไม่ใช้รายงานว่ามีเหตุในจังหวัดเดียวกันเป็น label ให้ทุกภาพ
- แยกตัวอย่างที่ผู้ตรวจตีความจากภาพ กับตัวอย่างที่มีหลักฐานยืนยันภาคสนามหรือแหล่งอิสระ
- แบ่ง train/validation/test โดยแยกเหตุการณ์ วันเวลา และพื้นที่ตามการทดลอง ป้องกัน tile จาก scene เดียวกระจายไปทั้ง train และ test
- ใช้ U-Net เป็นหนึ่งตัวเลือกตั้งต้นตามแผนในไฟล์ แล้วเปรียบเทียบกับ baseline; การเลือกโมเดลสุดท้ายขึ้นกับข้อมูลและผลทดลอง
- กำหนด threshold จาก validation แล้วตรึงก่อนทดสอบ test set
- บันทึกรุ่นโมเดล ชุดฝึก ชุดทดสอบ และผลประเมินให้เปิดดูได้
- ระยะเริ่มทดลอง score ของโมเดลให้เรียกคะแนนคัดกรอง การตีความเป็นความน่าจะเป็นต้องมีการทดสอบ calibration รองรับ
- ผู้ใช้แก้ขอบเขตให้เก็บเป็นข้อมูลสำหรับทบทวนชุดฝึก ไม่เทรนโมเดลใหม่เงียบ ๆ ระหว่างใช้งาน

**เงื่อนไขก่อนแสดงเป็นฟังก์ชันใช้งานจริง:** มีชุดทดสอบที่แยกจากชุดฝึก มีนิยามการตรวจพบและการแจ้งผิด มีผลแยกตามเหตุ/เงื่อนไข และผู้ตรวจใช้ผลบนแผนที่ตรวจย้อนกลับได้ ถ้ายังไม่มีหลักฐานหรือชุดข้อมูลพอ ให้ส่งมอบรุ่น A/B ตามความสามารถที่พิสูจน์แล้ว

### 10.3 ความทนทานและความปลอดภัยที่จำเป็น

- เก็บ secret และ token เฉพาะ backend ไม่ใส่ใน JavaScript, รายงาน, log หรือ export
- สร้าง job key จาก input และพารามิเตอร์ ป้องกันการกดซ้ำสร้างงานและผลซ้ำ
- จัดการ token หมดอายุ 429, timeout, 5xx และการเริ่ม worker ใหม่ โดยมี retry จำกัดจำนวนและ backoff
- ถ้าล้มเหลวแสดงสถานะล้มเหลว ไม่คืนค่า 0 แทนผลตรวจ
- ภาพที่เคยโหลดเปิดจาก cache ได้ โดยแสดงเวลาต้นทางและสถานะข้อมูลที่เก็บไว้
- ตรวจชนิดและขนาดไฟล์แนบ ตรวจ polygon และใช้รายการโดเมนที่อนุญาตสำหรับการดึง asset จาก provider
- ระบบหลายผู้ใช้แยกผู้ดู ผู้บันทึก/ตรวจ และผู้ดูแล; เก็บ audit ในการแก้ขอบเขต/สถานะ
- สำรองทั้งฐานข้อมูลและไฟล์ที่เชื่อมกัน และทดสอบกู้คืนเหตุการณ์ตัวอย่างหนึ่งชุด

## 12. แผนทดสอบ

### 12.1 การเชื่อมข้อมูลและระบบ

- ภาพจริงอย่างน้อยหนึ่ง acquisition ของแต่ละแหล่งที่เปิดใช้ ต้องตรวจ product ID, วันเวลา, footprint และตำแหน่งบนแผนที่
- สร้างชุดตรวจการทำงานที่มีภาพครอบคลุมเต็ม บางส่วน มีเมฆ/nodata ไม่มีภาพ และคำขอขัดข้อง โดยบันทึกว่าสถานการณ์ใดมาจากข้อมูลจริงหรือการจำลองข้อผิดพลาด
- ตรวจ polygon เทียบตำแหน่งในเครื่องมือ GIS หรือผลอ้างอิงเดียวกัน ทดสอบพื้นที่และหน่วยแปลง
- บันทึก observation/review/evidence แล้วโหลดหน้าใหม่และเริ่มระบบใหม่ ต้องอ่านกลับได้ครบ
- ส่งออกแล้วนำเข้ากลับ ต้องคงพิกัด แหล่งข้อมูล วันเวลา ประเภทข้อมูล และสถานะ
- กดงานซ้ำและลองใหม่หลังล้มเหลว ต้องไม่สร้างผลซ้ำ
- ตรวจ API ขัดข้องและ mask ว่าง ต้องไม่ถูกตีความว่าไม่มีน้ำมัน
- ทดลองเปิดและค้นหาทั้ง desktop และหน้าจอแคบ ส่วนที่อ่าน/แนบหลักฐานต้องใช้ได้

### 12.2 การประเมินคัดกรอง/AI

เปรียบเทียบวิธี A ผู้ใช้ตีความ, B baseline, C โมเดลที่เลือก ด้วยข้อมูลทดสอบชุดเดียวกันและ protocol ที่ตรึงไว้

ตัวชี้วัดหลัก: Precision ของข้อเสนอที่ตรวจได้, Recall ต่อเหตุที่มีหลักฐาน, F1, IoU/Dice ของขอบเขตที่มี label เพียงพอ และจำนวนการแจ้งผิดต่อพื้นที่/scene ที่ประเมินได้

ต้องกำหนดการจับคู่ผลกับเหตุจริงและ threshold ของการทับซ้อนก่อนวัด จำนวนและสัดส่วนตัวอย่าง รายเหตุ วันเวลา และข้อจำกัดของ ground truth ต้องรายงาน ไม่มีชุดทดสอบเพียงพอให้เรียกผลว่าการทดลองนำร่อง

เก็บกรณี false positive และ false negative โดยแยกเงื่อนไข เช่น ใกล้ชายฝั่ง ข้อมูลบางส่วน ภาพต่าง orbit และบริเวณที่สัญญาณคล้ายกัน การสุ่ม tile จากภาพเดียวอย่างเดียวไม่ใช้ยืนยันว่าโมเดลใช้ได้กับเหตุใหม่

### 12.3 การทดสอบผู้ใช้และการใช้ตัดสินใจ

งานที่ให้ผู้ใช้ทำ: เลือกภาพที่ตรวจได้ → หาตำแหน่ง → วงขอบเขต → บันทึกเหตุ → ส่งออกคำขอสำรวจ → แนบผลตรวจ → อธิบายสถานะและวันเวลาของข้อมูล

วัดเวลาจบงาน สัดส่วนทำสำเร็จ จำนวนข้อผิดพลาด และความเข้าใจเรื่องพื้นที่สงสัยกับพื้นที่ยืนยัน เปรียบเทียบ workflow เดิม เช่น Browser/GIS กับ dashboard โดยใช้ภาพและโจทย์เดียวกัน แยกเงื่อนไข cache/อินเทอร์เน็ตให้เป็นธรรม

ข้อเสนอของผู้ช่วย: เริ่มผู้ทดลอง 3–5 คนเพื่อแก้ workflow จากนั้นขยายการประเมินตามกลุ่มเป้าหมาย ในไฟล์เสนอผู้เชี่ยวชาญ 20 คนและ SUS ซึ่งเป็นแผนการประเมิน ไม่ใช่จำนวนที่ได้ทดสอบแล้ว

## 13. ลำดับพัฒนาและจุดตรวจรับ

เวลาต่อไปนี้เป็นประมาณการของผู้ช่วย สมมติผู้พัฒนาหลักหนึ่งคนที่ทำเว็บและ Python ได้ มีเครื่องพร้อมและข้อมูลเข้าถึงได้แล้ว นับเป็นวันทำงาน ไม่รวมรอสิทธิ/ผู้เชี่ยวชาญ/ชุดข้อมูล/การสำรวจ และยังไม่เป็นกำหนดส่งที่ผู้ใช้ยืนยัน

| ระยะ | งาน | ผลส่งมอบและเกณฑ์ผ่าน | เวลาประมาณ |
|---|---|---|---|
| 0 กำหนดขอบเขต | เลือก AOI, รูปแบบใช้งาน, บัญชีข้อมูล, ตรวจต้นแบบ และวาง schema/API | ขอบเขตและวิธีเข้าถึงข้อมูลชัด ทดลองค้นภาพและขอภาพขนาดเล็กได้ | 2–3 วัน |
| 1 เชื่อมภาพจริง | catalogue, adapter ภาพ, cache, ชั้นแผนที่, metadata/quality และสถานะข้อผิดพลาด | ภาพจริงอยู่ตรงพิกัด เลือกวันที่ได้ รู้ product/เวลา และเปิดภาพเดิมซ้ำได้ | 5–8 วัน |
| 2 MVP เหตุการณ์ | ฐานข้อมูล วาด/แก้ polygon รายการเหตุ review/evidence คำขอสำรวจ และ export | workflow ตั้งแต่เลือกภาพถึงส่งออกและแนบผลตรวจใช้ได้ครบ ข้อมูลอยู่หลัง restart | 7–10 วัน |
| 3 baseline | เตรียม SAR, water mask, anomaly candidates, review และบันทึก run | ผลคัดกรองตรวจย้อนกลับได้ และมีรายงานเทียบกับผู้ใช้บนชุดนำร่อง | 5–8 วัน หลังมีภาพและ label |
| 4 AI | จัดชุดข้อมูล เทรน/ประเมิน/ตรึง threshold และเชื่อม worker | ผ่านเกณฑ์ประเมินที่ตกลงตามข้อมูลจริงก่อนใช้เป็นผลคัดกรองหลัก | 10–20 วันขึ้นไปหลังข้อมูลพร้อม |
| 5 ทดลองใช้และเตรียมนำเสนอ | แก้ workflow ทดสอบกู้คืน เก็บตัวชี้วัด ทำรายงาน/ชุดสาธิต | ผู้ใช้ทำโจทย์ครบ มีหลักฐานผลทดสอบและข้อมูลสาธิตที่อ้างที่มาได้ | 3–5 วัน |

ระยะ 0–2 ให้ MVP ที่ใช้ข้อมูลจริงและผู้ใช้ตรวจเอง ประมาณ 14–21 วันทำงานภายใต้สมมติฐานนี้ AI เป็นเส้นงานวิจัยแยกซึ่งระยะเวลาขึ้นกับชุดข้อมูล ไม่ควรใช้เวลาสร้างหน้าเว็บไปประมาณเวลาทำโมเดลทั้งหมด

ลำดับก่อนหลัง: สิทธิข้อมูล → ภาพจริงและพิกัด → การบันทึกและตรวจสอบ → ชุดข้อมูล/เกณฑ์ประเมิน → baseline/AI → การขยายการเชื่อมโดรน งานวาง schema และแก้หน้าจอทำควบคู่การตรวจสิทธิได้

## 14. Backlog ตามความสำคัญ

**P0 — ต้องมีเพื่อส่งมอบ MVP**

- ขอบเขตนำร่องและการค้นภาพที่มีข้อมูลจริง
- แผนที่พิกัดจริง แหล่งภาพและวันเวลา พร้อมสถานะภาพที่ประเมินไม่ได้
- วาดและบันทึกขอบเขต คำนวณพื้นที่ถูกวิธี และเปิดกลับได้
- incident/observation แยกกัน และมีหลักฐานการเปลี่ยนสถานะ
- แนบผลตรวจและส่งออก GeoJSON/CSV พร้อมแหล่ง/เวลา
- เก็บข้อมูลจริงกับตัวอย่างแยกกัน รักษา credential ฝั่ง server
- cache, สถานะล้มเหลว, การป้องกันข้อมูลซ้ำ และสำรอง/กู้คืน

**P1 — เพิ่มประโยชน์การสำรวจและการทดลอง**

- เปรียบเทียบภาพสองเวลาและคุณภาพภายใน AOI
- SAR baseline, รายการผลให้ตรวจ และประวัติการแก้ไข
- บริบทพื้นที่เปราะบางที่มีแหล่งข้อมูลจริง และคิวสำรวจที่อธิบายเหตุผลได้
- ชุดข้อมูลและรายงานประเมินโมเดลแยกจากข้อมูลฝึก
- รายงานเหตุและสรุปสถิติที่นิยามชัด

**P2 — งานต่อยอดที่มีเงื่อนไขเพิ่มเติม**

- การรับ telemetry และ live video จากโดรน
- ข้อมูลกระแสน้ำ/ลมและแบบจำลองการเคลื่อนที่ที่ประเมินแล้ว
- การสร้าง flight mission ตามอุปกรณ์จริงและกระบวนการอนุมัติภารกิจ
- การคำนวณ dose จากผลทดลองวัสดุและการเชื่อมผล TPH/ชีวบำบัด
- การเปิดหลายพื้นที่/หลายทีม ระบบแจ้งเตือนภายนอก และการขยายการประมวลผล

การตั้งรอบอัปเดต การเปิดเผยระบบภายนอก หรือการส่งแจ้งเตือนจริงเป็นการตัดสินใจในระยะใช้งาน ไม่ได้ถูกดำเนินการโดยเอกสารแผนนี้

## 15. ทรัพยากรและค่าใช้จ่ายที่ต้องเตรียม

| รายการ | จำเป็นเมื่อไร | วิธีลดภาระตั้งต้น |
|---|---|---|
| บัญชีและ OAuth ของข้อมูล | เมื่อขอภาพผ่านวิธีที่เลือก | ทดสอบคำขอเล็กก่อน เก็บ secret ฝั่ง server |
| เครื่องพัฒนาและพื้นที่เก็บ | ทุกระยะ | หนึ่ง AOI, crop เท่าที่จำเป็น, cache ตาม scene/parameter |
| เครื่อง/เซิร์ฟเวอร์และฐานข้อมูล | MVP ที่ต้องเปิดใช้ต่อเนื่อง | เริ่ม local/private แล้วเลือก hosting ตามผู้ใช้งาน |
| GPU หรือเวลาประมวลผลฝึก | ระยะ AI หากโมเดลต้องการ | ประเมิน baseline ก่อนและกำหนดชุดทดลอง |
| ผู้รู้ remote sensing | ตรวจ pipeline SAR และ label | นัดทบทวนตัวอย่าง/เงื่อนไขก่อนขยายข้อมูล |
| ผู้สำรวจ/ภาพโดรน | หลักฐานยืนยันและประเมิน end-to-end | ใช้หลักฐานย้อนหลังที่มีสิทธิและวันเวลาชัดก่อน |
| เวลาเก็บ label และตรวจข้อผิดพลาด | baseline/AI | จัดมาตรฐานการตรวจและเก็บกรณีไม่แน่ชัด |

ยังไม่เสนอราคาจริง เพราะยังไม่มีจำนวนภาพ ขนาด AOI รูปแบบ hosting และทรัพยากรทีม ต้องบันทึกการใช้คำขอ พื้นที่เก็บ และเวลา compute จากการทดลองแรกก่อนจัดงบ

## 16. ความเสี่ยงที่เกี่ยวข้องกับงานและวิธีรับมือ

| ประเด็น | ผลต่อระบบ | วิธีรับมือและหลักฐานที่ต้องเก็บ |
|---|---|---|
| ไม่มีภาพที่เหมาะกับวันที่ต้องการ | งานตรวจจากดาวเทียมทำต่อไม่ได้ในช่วงนั้น | แสดงวันล่าสุดที่มี/พื้นที่ประเมินไม่ได้ และแนบหลักฐานภาคสนาม |
| สัญญาณคล้ายคราบน้ำมัน | แจ้งผิดและเสียเวลาสำรวจ | สถานะสงสัย, เก็บ hard negatives, review และวัด false alarms |
| ไม่มี label ยืนยันเพียงพอ | ประเมิน AI อย่างน่าเชื่อถือไม่ได้ | ส่งมอบ manual MVP และเรียกผลคัดกรองว่าการทดลองจนข้อมูลพร้อม |
| ข้อมูลภาพและภาคสนามต่างเวลา | หลักฐานอาจไม่ตรงกับภาพ | แสดงเวลาทั้งคู่และให้ผู้ตรวจอธิบายการเชื่อมโยง |
| geometry/พื้นที่ผิด | ส่งพื้นที่สำรวจผิดและตัวเลขผิด | ตรวจ CRS, transform, nodata และเทียบใน GIS |
| โควตา/อินเทอร์เน็ต/บริการขัดข้อง | เตรียมภาพไม่สำเร็จ | cache, job/retry, จำกัดคำขอ และสถานะข้อผิดพลาดชัด |
| ขอบเขตงานขยายเร็ว | MVP ส่งมอบช้า | ตรวจรับ P0 ก่อน P1/P2 และแยกเวลาเก็บข้อมูลออกจากเวลาเขียนเว็บ |

## 17. ผลส่งมอบสำหรับ iENA ที่เสนอ

- dashboard ใช้ภาพจริง พร้อมบัญชีแหล่งและวันเวลา
- ชุดกรณีศึกษาที่ผู้ใช้ตรวจย้อนกลับจากเหตุ → ขอบเขต → ภาพ → หลักฐานได้
- workflow สาธิตเลือกภาพ วงจุด เปิดเหตุ ส่งออกพิกัด และแนบผลสำรวจ
- รายงานทดสอบการเชื่อมข้อมูล พิกัด/พื้นที่ การบันทึก การใช้งาน และการกู้คืน
- ถ้ามี baseline/AI: รายงานชุดข้อมูล วิธีแบ่งชุด ผลตรวจพบ/แจ้งผิด และตัวอย่างความล้มเหลว
- ตัวอย่างรายงานและไฟล์ GeoJSON/CSV ที่เปิดในเครื่องมืออื่นได้
- ชุดภาพและ metadata ที่เก็บไว้สำหรับนำเสนอเมื่ออินเทอร์เน็ตไม่พร้อม โดยป้ายเวลาและที่มายังคงเดิม; ผลจำลองมีป้ายแยก
- คำอธิบายว่า dashboard ช่วยส่งต่อข้อมูลให้ระบบโดรน/ชีวบำบัดส่วนใด และส่วนใดได้รับการทดสอบแล้ว

ผลที่กล่าวได้ต้องสอดคล้องกับสิ่งที่ทดสอบ เช่น ลดเวลารวบรวมและส่งต่อพื้นที่สำรวจตามการทดลองที่มี ไม่อ้างว่าการมี dashboard หรือ AI เท่ากับกำจัดน้ำมันสำเร็จ และการเชื่อมดาวเทียมกับโดรนอย่างเดียวไม่ใช้ยืนยันความใหม่ระดับโลก

## 18. แหล่งเว็บที่ตรวจประกอบแผน

ตรวจเอกสารทางการเมื่อวางแผนวันที่ 4 ตุลาคม 2026 ค่าโควตาและรูปแบบ API ต้องตรวจอีกครั้งก่อน implementation

1. [Copernicus STAC catalogue](https://documentation.dataspace.copernicus.eu/APIs/STAC.html) — การค้นหา product และ metadata ตามพื้นที่/เวลา
2. [Sentinel Hub](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub.html) และ [Process API](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub/Process.html) — วิธีขอภาพ/ข้อมูล
3. [Sentinel-1 GRD](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub/Data/S1GRD.html) — backscatter, calibration, speckle และ geometry
4. [Authentication](https://documentation.dataspace.copernicus.eu/APIs/SentinelHub/Overview/Authentication.html) — OAuth และ token
5. [Quotas and limitations](https://documentation.dataspace.copernicus.eu/Quotas.html) — ข้อจำกัดของบริการ
6. [SentiWiki Sentinel-2 mission](https://sentiwiki.copernicus.eu/web/s2-mission) — ความละเอียดและรอบการเก็บภาพ
7. [ESA Oil Slicks](https://knowledge-hub-gda.esa.int/eo_capability/oil-slicks/) — บทบาท SAR/optical และ look-alikes
8. [OpenLayers GeoJSON example](https://openlayers.org/en/latest/examples/geojson.html) — ชั้นข้อมูล vector
9. [FastAPI Background Tasks](https://fastapi.tiangolo.com/tutorial/background-tasks/) — แนวทางแยกงานคำนวณหนัก
10. [PostGIS ST_Area](https://postgis.net/docs/manual-3.7/en/ST_Area.html) — การคำนวณพื้นที่และหน่วย

## 19. สิ่งที่ต้องกำหนดก่อนลงมือระยะ 0

| เรื่อง | สมมติฐาน/สถานะปัจจุบัน | ผลต่อแผน |
|---|---|---|
| พื้นที่นำร่อง | ยังไม่เลือก; ระยองเป็นตัวอย่างจากต้นแบบ | การค้นภาพ ชายฝั่ง และหลักฐาน |
| ระดับรุ่นแรก | เสนอภาพจริงและผู้ใช้ตรวจเป็นฐาน | ลดการพึ่งพาชุดฝึก AI ใน MVP |
| วันส่ง/วันสาธิต | ยังไม่ทราบ | เลือก P0/P1 ให้เหมาะกับเวลาที่เหลือ |
| ผู้พัฒนาและเครื่อง | ยังไม่ทราบ | ปรับประมาณการและงาน GPU |
| บัญชีดาวเทียม | ยังไม่ตรวจการตั้งค่าของผู้ใช้ | การขอภาพจริงตามวิธีที่เลือก |
| ชุดภาพ/label/ผู้ตรวจ | ยังไม่ยืนยันว่ามี | เปิดหรือเลื่อน baseline/AI ตามหลักฐาน |
| การเชื่อมโดรน | รุ่นแรกส่งออกข้อมูลพื้นที่และแนบผล | รูปแบบ mission/telemetry ทดสอบภายหลังตามอุปกรณ์ |
| รูปแบบใช้งาน | เสนอ local/private สำหรับเริ่มทดลอง | hosting, สิทธิผู้ใช้ และการสำรองข้อมูล |

รายการนี้เป็นข้อมูลที่รอกำหนดสำหรับ implementation งานวางแผนและการออกแบบข้างต้นดำเนินได้จากข้อมูลที่มีแล้ว
